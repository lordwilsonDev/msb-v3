## H07 — AuditChain: tamper detection works, recovery does not exist

**Evidence artifact:** `artifacts/hygiene/h07_auto_healing_*.json`
**Runner:** `scripts/hygiene/h07_auto_healing_runner.py`

### Root cause

`src/msb_v3/uac/audit_chain.py` implements a hash chain with two methods:
`append()` and `verify_chain()`. There is **no** `auto_heal()`, **no**
cascade-rewrite, and **no quarantine mode** for a compromised chain.

The experiment proves the failure mode precisely:

| step | result |
|------|--------|
| baseline (0 records) | `valid: true` |
| after 5 appends | `valid: true` |
| tamper seq=3 payload (SQLite UPDATE, no hash recompute) | `valid: false`, broken at seq=3, "stored hash does not match recomputed content hash" |
| delete seq=3 + append new record | `valid: false`, broken at seq=4, "prev_hash does not match preceding record" |

Detection works (`verify_chain()` catches the tamper at seq=3). Recovery
does **not** work: deleting the bad record leaves seq=4's `prev_hash`
pointing at the deleted record's hash, so the chain is permanently broken
from that point forward.

### Why this matters

An audit chain that can be detected-but-not-recovered is a **single point of
no return**: one compromised record silently converts the entire tail of the
chain into untrustworthy history. For a system whose stated purpose is
"tamper-evident audit trail", detection without a recovery or quarantine
story is incomplete.

### ✅ Resolved (2026-08-09)

`AuditChain` now implements both fix options:

- **`quarantine()`** — explicitly marks a compromised chain (state, broken
  seq, reason, timestamp in a `chain_meta` table). Never silent: a
  quarantined chain still verifies as broken until repair.
- **`repair()`** — checkpoint cascade-rewrite: re-anchors at the last
  verified record, recomputes the tail from the first break forward, and
  appends an auditable `chain.repaired` event so recovery is itself
  audit-trailed.

Verified by 5 new pytest cases in `tests/uac/test_audit_chain.py` and the
h07 runner (now `pass`).

### Fix options (in priority order)

1. **Quarantine + rebuild:** add a `quarantine()` that (a) marks the
   compromised chain as quarantined in the DB, (b) freezes verification of
   the corrupted prefix, (c) starts a fresh chain segment — documented and
   explicit, never silent.
2. **Cascade-rewrite (checkpoint recovery):** on tamper, re-anchor from the
   last verified record, rewrite the tail with recomputed hashes, and record
   an explicit "chain repaired" audit event so the rewrite itself is
   auditable.
3. **Both:** quarantine is the safe default; cascade-rewrite is the
   recovery path under operator control.

**Acceptance test:** the h07 runner must flip from `fail` to `pass` — i.e.
after tamper, either `heal_succeeded == true` or an explicit quarantine mode
exists and the subsequent records remain verifiable.

## H10 — /register accepts oversized payloads

**Evidence artifact:** `artifacts/hygiene/h10_resource_chaos_*.json`
**Runner:** `scripts/hygiene/h10_resource_chaos_runner.py`

### Root cause

The chaos run sent a ~1MB truth entity payload to the truth-registry write
path. Expected: reject with `413` or `400`. Observed on the **correct**
endpoint (`POST /business/register`, verified live 2026-08-09): **`200` —
fully accepted** with no size rejection.

> Runner correction: an earlier runner version used the unprefixed
> `/register` path (404 — the router is mounted at `/business`), which
> produced a misleading `oversized_status=404`. Re-pointed to
> `/business/register`, the real behavior is measured: **200 accepted**.

The failing assertion in the latest artifact:
```
expected_behavior: /business/register rejects oversized payloads with 413 or 400
actual_behavior:  oversized_rejected=False (oversized_status=200)
verdict: fail
```

Root cause: **no payload-size enforcement exists** on `/business/register`
(or any truth-registry write path). A 1MB payload is accepted and written in
full — the server neither limits nor rejects with a size error.

### Why this matters

Without a declared size limit (and a `413`/`422` response), the truth
registry has no bound on entity growth: a single bad client or bug can write
a multi-hundred-MB "truth" record, and monitoring has no signal — it looks
like a routing error, not an abuse/DoS signal.

### ✅ Resolved (2026-08-09)

`/business/register` now enforces `MAX_PAYLOAD_BYTES` (256 KiB default,
overridable via `MSB_MAX_PAYLOAD_BYTES`): oversized payloads are rejected
with `413 Payload Too Large` and a structured error. Verified live (1MB
payload → 413) and by the h10 runner (now `pass`).

### Fix options

1. **Declared limit + 413:** enforce a max payload size (e.g. 256KB) at the
   FastAPI body boundary for `/register` and return `413 Payload Too Large`
   with a structured error.
2. **422 validation:** if the limit is semantic (field-level), reject with
   `422 Unprocessable Entity` and a field error.
3. **Document the limit** in the OpenAPI schema so clients and the contract
   fuzzer share one source of truth.

**Acceptance test:** the h10 runner must flip from `fail` to `pass` — i.e.
oversized payload rejected with `413`/`400`/`422`, service stays alive, and
the 200-request burst stays under the latency budget.
