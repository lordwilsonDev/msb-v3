# MSB v3.3 — Feature Plan

**Date**: 2026-08-26
**Baseline**: v3.2 (CI green, 2248 tests, 37 subsystems, PLEI 7-phase verified)
**Thesis**: v3.0 built, v3.1 hardened, v3.2 proved — v3.3 makes it **useful**.

---

## Where We Are

| Version | What It Did | Tests |
|---------|-------------|-------|
| **v3.0** | PLEI 7-phase, provider seam, governance, 37 subsystems | 1877 |
| **v3.1** | DB versioning, structured logging, xdist, local inference | 2152 |
| **v3.2** | Verification gaps closed, smoke tests for every subsystem | 2248 |

The system is built, hardened, and verified. But it's **not yet learning from itself** and has **no runtime observability**. That's what v3.3 changes.

---

## What v3.3 Must Do

### 1. Observability Subsystem — 0 tests, 0 dashboards

The only subsystem with **zero tests**. We have 37 subsystems, 207 API routes, and no way to answer "what's the system doing right now?"

Need:
- Structured metrics collection (latency, error rate, throughput per subsystem)
- Health endpoint that returns real subsystem status (not just "server up")
- Test proving metrics accumulate correctly
- Test proving health endpoint returns actual subsystem states

**Effort**: 2 days
**Impact**: First time we can observe the system without reading logs

---

### 2. PLEI Learning Loop — Make Predictions Actually Learn

28 prediction/outcome pairs exist. The calibration engine is built. But **nothing feeds predictions in automatically** and **nothing records outcomes**. PLEI currently predicts but never checks if it was right.

Need:
- Factory gate records a prediction before each CI run (test count, pass rate, duration)
- Test suite records outcomes after each CI run (actual pass rate, actual duration)
- Calibration report generated from accumulated data
- Test proving the prediction → outcome → error → adjustment cycle works end-to-end

**Effort**: 2 days
**Impact**: PLEI goes from "engine that could predict" to "engine that gets smarter"

---

### 3. BitNet Local Inference — Unblocked

i2_s quant was incompatible with llama.cpp build 10200. Two paths:

**Path A**: `brew upgrade llama.cpp` when newer build ships (supports i2_s)
**Path B**: Use Ollama with the existing qwen3:8b model (already working) as the local inference backend

For v3.3, document Path B as the working solution. Path A when upstream catches up.

Need:
- Integration test proving Ollama local inference works via LlamaCPPClient
- Config documentation for switching between providers
- Test proving provider switching works (Ollama → stub → Ollama)

**Effort**: 0.5 day
**Impact**: Local inference is documented and tested, not just "working by accident"

---

### 4. Memory Consolidation — Deprecation Path

Three memory systems remain:
- `memory/store.py` — legacy simple store
- `memory_fabric/` — primary (provenance, verification, consolidation)
- `retrieval/` — query layer on top of fabric

Phase 3 tests proved the fabric → retrieval pipeline. Now we need the cleanup.

Need:
- Deprecation warnings on `memory/store.py` (point users to `memory_fabric`)
- Single documented interface in `memory_fabric/README.md`
- Test proving `memory_fabric` is the canonical path
- Test proving `memory/store.py` still works but warns

**Effort**: 1 day
**Impact**: No more "which memory system?" confusion

---

### 5. Self-Healing Observability — The Flywheel Closes

The flywheel subsystem exists (31 tests) but operates in isolation. Connect it to observability.

Need:
- Flywheel consumes observability metrics (latency, error rate)
- Flywheel proposes optimizations based on observed patterns
- Test proving flywheel → optimization → measurable improvement cycle
- Dashboard showing flywheel recommendations and their outcomes

**Effort**: 2 days
**Impact**: System doesn't just observe itself — it improves itself

---

### 6. Evidence Chain Verification — End-to-End

The evidence spine has tamper-evident hash chains. But we haven't verified the full chain from action → evidence → audit → replay in a single test.

Need:
- Test proving: action executed → evidence recorded → hash chain intact → replay produces identical result
- Test proving: tampered evidence is detected
- Test proving: audit trail is complete for a governed action

**Effort**: 1 day
**Impact**: Evidence chain is proven, not just claimed

---

## Priority Order

```
Phase 1 (Days 1-2): Observability + Evidence
  1. Observability subsystem (metrics, health, tests)
  2. Evidence chain end-to-end verification

Phase 2 (Days 3-4): Learning Loop
  3. PLEI prediction → outcome → calibration pipeline
  4. Flywheel → observability integration

Phase 3 (Days 5-6): Consolidation
  5. Memory deprecation path
  6. BitNet documentation + provider switching tests
```

## Anti-Scope-Creep Rules

1. **No new subsystems** — v3.3 connects existing pieces, doesn't create new ones
2. **No new API routes** — 225 routes is enough; make the existing ones observable
3. **No new providers** — the 10 existing providers cover the space; make them measurable
4. **No distributed anything** — single-node observability first
5. **No multimodal** — still storage-gated; don't repeat the disk crisis

## Definition of Done

v3.3 is done when:
- Every subsystem has at least 1 test (observability was the last holdout)
- PLEI calibration data grows automatically from CI runs
- The system can answer "what's slow right now?" from metrics
- The evidence chain is proven end-to-end with a single test
- Memory has one documented canonical path
- CI remains green throughout
- No new critical gaps introduced

## What v3.3 Is NOT

- Not a feature explosion (the 207 API routes are enough)
- Not a rewrite (connection, not revolution)
- Not multimodal (storage-gated until disk < 50%)
- Not distributed (single-node observability first)
- Not a new architecture (the architecture is solid; make it observable)
