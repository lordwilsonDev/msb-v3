**Date**: 2026-08-26
**Baseline**: v3.2 (CI green, 2248 tests, 37 subsystems, PLEI 7-phase verified)
**Thesis**: v3.0 built, v3.1 hardened, v3.2 proved — v3.3 makes it **useful**.

---

## Where We Are

| Version | What It Did | Tests |
|---------|-------------|-------|
| **v3.0** | PLEI 7-phase, provider seam, governance, 37 subsystems | 1877 |

## What v3.3 Must Do

### 1. Observability Subsystem — 0 tests, 0 dashboards

The only subsystem with **zero tests**. We have 37 subsystems, 207 API routes, and no way to answer "what's the system doing right now?"

**What exists:** `metrics.py` has Prometheus counters/gauges/histograms (`QUERIES`, `LATENCY`, `READY`, `ACTIVE_CONNECTIONS`, etc.) but no test coverage and no health endpoint.

Need:
- Health endpoint that probes each subsystem and returns structured status (not just "server up")
- Test proving the existing Prometheus metrics accumulate correctly
- Test proving health endpoint returns real subsystem states

**Effort**: 1.5 days
**Impact**: First time we can observe the system without reading logs

---

### 2. PLEI Learning Loop — Make CI Predictions Actually Learn

28 prediction/outcome pairs exist in `.plei/calibration.jsonl` — but these are **project lifecycle predictions** (P50/P80/P95 completion days). The CI learning loop is a **different pipeline** that doesn't exist yet.

Need:
- Factory gate records a prediction before each CI run (test count, pass rate, duration)
- Test suite records outcomes after each CI run (actual pass rate, actual duration)
- Calibration report generated from accumulated CI data
- Test proving the prediction → outcome → error → adjustment cycle works end-to-end

**Effort**: 1.5 days
**Impact**: PLEI goes from "engine that could predict" to "engine that learns from CI"

---

### 3. BitNet Local Inference — Document What Works

i2_s quant was incompatible with llama.cpp build 10200. But **14 integration tests already exist** from v3.2 Tier 2 proving Ollama local inference works via LlamaCPPClient.

What's left is documentation, not code:
- Document Ollama as the working local inference backend
- Document provider switching (Ollama → stub → Ollama)
- Note BitNet status (blocked on `brew upgrade llama.cpp`)

**Effort**: 0.5 day
**Impact**: Local inference is documented, not just "working by accident"

---

### 4. Memory Consolidation — Deprecation Path

Three memory systems remain:
- `memory/store.py` — legacy simple store
- `memory_fabric/` — primary (provenance, verification, consolidation)
- `retrieval/` — query layer on top of fabric

Phase 3 tests proved the fabric → retrieval pipeline. Now we need the cleanup.

Need:
- Deprecation warnings on `memory/store.py` (point users to `memory_fabric`)
- Single documented interface in `memory_fabric/README.md`
- Test proving `memory/store.py` still works but warns

**Effort**: 0.5 day
**Impact**: No more "which memory system?" confusion

---

### 5. Flywheel Observability Integration — 4 Pieces

The flywheel (31 tests, 9-stage turn state machine) operates in isolation. It produces audit events and axiom records but **no Prometheus metrics** and **consumes no system health data**. This item is decomposed into 4 independently shippable pieces.

#### Piece 5a: Instrument flywheel stages with Prometheus metrics

Add to `flywheel/engine.py`:
- `msb_v3_flywheel_stage_seconds` — Histogram of stage duration (labels: stage)
- `msb_v3_flywheel_stage_total` — Counter of stage outcomes (labels: stage, result)
- `msb_v3_flywheel_active_turns` — Gauge of currently running turns
- `msb_v3_flywheel_approval_wait_seconds` — Histogram of approval wait time (labels: stage)

Instrument `start()`, `_exec_stage()`, `approve()`, and `_audit()`.

**Test:** Verify metrics accumulate after a stub turn runs.
**Effort**: 1 day

#### Piece 5b: Flywheel reads system health

Build `flywheel/health_bridge.py`:
- `system_health()` — returns API latency, error rate, subsystem status
- `should_pause()` — returns (pause, reason) based on system health (e.g., pause if API error rate > 50%)
- `recommended_charge_backend()` — returns 'sovereign' or 'stub' based on provider health

**Test:** Verify `should_pause()` returns True when error rate is high, False when healthy.
**Effort**: 1 day

#### Piece 5c: Flywheel health endpoint

Add `GET /flywheel/health` to the API:
- Active turn count, total completed, success rate
- Average stage latency, current stage distribution
- Last error, system health from bridge

**Test:** Verify endpoint returns structured status with real data.
**Effort**: 0.5 day

#### Piece 5d: End-to-end integration test

Prove the full loop:
1. Flywheel runs a stub turn → metrics accumulate
2. Health endpoint returns flywheel status
3. Health bridge reads system state
4. Metrics are visible in Prometheus format

**Test:** Single test proving flywheel → metrics → health endpoint → bridge works.
**Effort**: 0.5 day

**Total for Item 5**: 3 days (was 2 in v1 of the plan)

---

### 6. Evidence Chain Verification — End-to-End

The evidence spine (`evidence/spine.py`) has tamper-evident hash chains (parent_hash + content_hash + audit_seq). But we haven't verified the full chain from action → evidence → audit → replay in a single test.

Need:
- Test proving: action executed → evidence recorded → hash chain intact → replay produces identical result
- Test proving: tampered evidence is detected
- Test proving: audit trail is complete for a governed action

**Effort**: 1 day
**Impact**: Evidence chain is proven, not just claimed

## Anti-Scope-Creep Rules

1. **No new subsystems** — v3.3 connects existing pieces, doesn't create new ones
2. **No new API routes** — 225 routes is enough; add only `/flywheel/health`
3. **No new providers** — the 10 existing providers cover the space; make them measurable
4. **No distributed anything** — single-node observability first
5. **No multimodal** — still storage-gated; don't repeat the disk crisis
6. **No flywheel engine changes** — add metrics around stages, don't rewrite the state machine

## Definition of Done

v3.3 is done when:
- Every subsystem has at least 1 test (observability was the last holdout)
- Flywheel stages emit Prometheus metrics visible in `/metrics`
- Flywheel health endpoint returns real-time status
- Flywheel health bridge reads system health and can pause on degradation
- PLEI CI calibration data grows automatically from CI runs
- The evidence chain is proven end-to-end with a single test
- Memory has one documented canonical path
- CI remains green throughout
- No new critical gaps introduced

## What v3.3 Is NOT

- Not a feature explosion (the 207 API routes are enough)
- Not a rewrite (connection, not revolution)
- Not multimodal (storage-gated until disk < 50%)
- Not distributed (single-node observability first)
- Not a new architecture (the architecture is solid; make it observable)
- Not a flywheel rewrite (instrument the existing stages, don't change the state machine)
